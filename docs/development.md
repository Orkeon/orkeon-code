# Development

## The checks

| Command | What it proves | Needs |
|---|---|---|
| `npm test` | Every `*.test.ts` under `src/` and `tests/` passes (`node --test`, native type stripping), the dependency rule of `tests/architecture.test.ts` included | Node 24 |
| `npm run typecheck` | The whole project type-checks (`scripts/typecheck.mjs`, `tsc` over `tsconfig.json`, one line per error) | `npm ci` |
| `npm run bundle:check` | Every command and crew bundles with the runtime's esbuild flags, without any Node API | `npm ci` |
| `npm run check:provenance` | No marker of another product's material in the sources (`scripts/provenance-markers.json`); `-- --strict` also requires the baseline to be empty, as CI does | Node |
| `npm run docs:commands -- --check` | `docs/commands.md` matches the commands | Node |
| `npm run check` | All of the above | `npm ci` |
| `bash scripts/smoke-runtime.sh [--mode ...]` | The real REPL loads every command (`N loaded, 0 skipped, 0 conflicts`) | a runtime |
| `bash scripts/check-file-modes.sh` | Scripts are committed executable | git |
| `node scripts/render-prompts.mjs <dir>` | Writes every prompt as the model reads it (`tests/support/prompt-catalogue.ts`), to review a prompt change as a `diff -r` of two renders; `tests/prompt-contract.test.ts` checks the same catalogue | Node 24 |

CI (`.github/workflows/ci.yml`) runs, as separate steps on every pull request and push to `main`, the tests, the type
check, the bundle check, the provenance gate, `docs/commands.md` up to date and the file modes (that is
`npm run check` plus the file modes). `runtime-smoke.yml` runs the smoke on the pinned image every Monday, on demand
(`workflow_dispatch`), and on a pull request that touches `.orkeon-version`, `orkeon-code`,
`scripts/smoke-runtime.sh` or `src/commands/**`. Until Orkeon `1.0.0-rc.6` is
published, that image does not exist and the job fails: run the smoke in source mode instead,
`ORKEON_SOURCE=<path to an Orkeon checkout> bash scripts/smoke-runtime.sh --mode source`.

## Running a crew alone

```bash
bash scripts/run-crew.sh src/crews/git-commit/crew.ork.ts
ORKEON_CODE_WORKSPACE=~/src/app bash scripts/run-crew.sh src/crews/project-init/crew.ork.ts
bash scripts/run-crew.sh src/crews/_probe-codeintel/probe.ork.ts     # the code-intelligence probe
```

It uses the `orkeon` tool (`Orkeon.Scripting.Cli`, nuget.org, pinned in `.config/dotnet-tools.json`; the .NET SDK
that restores and runs it is pinned by `global.json`, like Orkeon's: `10.0.300` with `rollForward: latestFeature`) or the
`orkeon-runners` image, on the demo fixture unless `ORKEON_CODE_WORKSPACE` says otherwise. Both are the pinned
release: until `1.0.0-rc.6` is published, the script cannot run. That tool reads its script limits from
`Orkeon:Scripting:Limits`, not from the REPL's `Orkeon:Cli:ScriptCommands:Limits`
([Configuration](configuration.md#settings-orkeon-code-relies-on)).

The run is headless: nobody answers the permission gate's questions, and there are no session rules. With the gate
on, as the example settings set it, a call the mode would ask about is refused instead (the model reads
`DENIED: …`): `main-loop` launched without a mode runs in `default`, so its writes, commands and network reads are
refused. Give it a mode to let them run, e.g.
`--inputs '{"prompt":"…","permissionMode":"bypassPermissions"}'`, on a project you can afford to change. The same command run
unattended, from a scheduler, a CI job or an application: [Autonomous and embedded runs](headless.md).

## Typings

`src/crews/.orkeon/orkeon.d.ts` and `src/commands/.orkeon/orkeon-cli.d.ts` describe the runtime API. They are
generated by `orkeon typings` from the pinned version: `npm run typings`, never edited by hand. For a version not
published yet, `ORKEON_SOURCE=<path to an Orkeon checkout> npm run typings` generates them from that checkout, the
same variable the launcher's source mode reads.

## Upgrading Orkeon

The runtime version lives in three places that must agree (`tests/version.test.ts` checks the first two):

1. `.orkeon-version`: the image tag and the version the launcher announces;
2. `.config/dotnet-tools.json`: `orkeon.scripting.cli`;
3. `package.json`: `esbuild`, pinned to the version the runtime bundles with
   (`tools/scripting-esbuild/package-lock.json` in Orkeon/orkeon at that tag);
4. `global.json`: the .NET SDK, the same pin as Orkeon's `global.json` at that tag (`tests/version.test.ts`
   checks it).

Then `npm ci && npm run typings && npm run check && bash scripts/smoke-runtime.sh`, and a live session on the demo
fixture (`/init`, `/assistant`, `/commit`, `/review`) before merging. Dependabot leaves esbuild alone for that reason.

## Releasing

1. Move the `[Unreleased]` entries of `CHANGELOG.md` under `## [x.y.z] - YYYY-MM-DD`.
2. Bump `package.json` `version` and `CLI_VERSION` in `src/commands/_lib/meta.ts` (the test keeps them equal), and
   the release notes in the same file.
3. Merge, then tag `vx.y.z` on `main` and push the tag: `release.yml` checks that the tag matches, runs the checks
   and the strict provenance gate, and publishes the GitHub Release with the source archives, `SHA256SUMS` and a
   build provenance attestation (`gh attestation verify <file> --repo Orkeon/orkeon-code`).

A version with a suffix (`-alpha.1`, `-rc.1`) is published as a pre-release.
